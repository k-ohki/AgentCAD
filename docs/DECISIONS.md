# 設計判断の記録

## D1 ロジックはすべて Python、UI は写し
Tauri/Three.js 側に状態を持たせない。テストを Python だけで完結させ、長期開発に耐える。

## D2 ソルバは自作し、スケッチと合致で共用
主目的が 機械系 3D CAD の中核機能の実装であるため。python-solvespace は将来、正解比較用に使う。

## D3 カーネルは抽象IFの裏に置き、差し替え可能にする
usd-brep を第一候補とするが、R5（履歴）・R6（三角形→面）が満たせなければ OCCT に切り替え、
USD は保存形式としてのみ使う。上位層はIFしか使わないので影響しない。

## D4 ヤコビアンは当面、拘束ごとの中心差分（廃止 → D10）
実装量を抑えるため。性能が問題になった拘束から解析解に置き換える（Constraint.jacobian を上書き）。

## D5 Undo はスナップショット方式
ドキュメントが JSON で小さいうちは最も単純で確実。大きくなったら差分コマンド方式へ移行する。

## D6 開発順序の変更（2026-11-08）
開発環境に usd-brep/OCCT が無い（ネットワーク制限）ため、カーネル非依存の
ソルバ → スケッチ → フィーチャーツリーを MockKernel で先に完成させた。

## D7 冗長判定は「自由度を1つも奪わない拘束」だけ
同心 + 平面一致のように一部だけ従属する組み合わせは一般的な 3D CAD でも正常扱いなので、
ランクが全く増えない（かつ満たされている）拘束だけを冗長とする。満たされない拘束は矛盾。

## D8 姿勢は四元数 + 正規化拘束
オイラー角の特異点を避ける。|q|=1 を拘束に入れて自由度を 6 に保つ。

## D9 合致の残差数 = 外す自由度数
平行は「a に垂直な2軸への b 方向の射影 = 0」の2残差にする（外積3成分だとランク落ちし冗長と誤判定する）。

## D10 ソルバを作り直す（2026-11-11）。D4 は廃止
実測で 400 変数のドラッグに約 7 秒かかり、定義状態も誤判定していた（PLAN.md 4章）。
- ヤコビアン: 拘束ごとの差分 → 種類ごとのバッチ自動微分（正確・速い・解析微分を手で書かない）
- 線形代数: 密な lstsq → 双対形式 LM + 疎行列
- 診断: 拘束ごとに SVD → 1 パスのグラム・シュミット
残差は「滑らかで、解で勾配が 0 にならない」形に書く。`abs()` は使わず向きを符号で持つ。

## D11 ドラッグは重み付き最小ノルム解
「目標を硬い拘束にして解く → 失敗したら別経路」をやめ、掴んだ変数の移動コストを上げて
通常の求解をする 1 経路にした。届かない場合も自然に近い点で止まる。

## D12 端点での正接は「半径方向 ⟂ 線」
線の端点が円上にあると「中心から線までの距離 = 半径」は重根になり、ヤコビアンが 0 になる
（長穴が「自由度 4・過剰定義」と誤判定された）。端点が円上にあると分かる場合は定式化を切り替える。

## D13 合致の向きは残差に入れず、事前位置合わせ + 事後確認
向きを残差に入れるとランク落ち（D9）か不連続になる。求解前に部品を正しい側へ回して初期値を作り、
求解後に確認して逆なら flipped として報告する。向きを問うのは平面-平面だけ（軸に向きはない）。

## D14 参照の解決を 1 か所に集約し、壊れたら候補を出す
命名は必ずどこかで壊れる前提に立つ。完全一致 → `#n` 違いで候補 1 つなら救済（警告）→
それ以外は候補つきのエラー、の順。UI で付け直せるようにする。

## D15 カーネルは適合テストで受け入れる
要件 R1〜R7 を `tests/test_kernel_conformance.py` にした。アダプタの完成条件が明確になり、
usd-brep と OCCT の切り替え判断も「通るかどうか」でできる。

## D16 API は UI と同時に作る（縦切り）、Tauri は最後
使う側が無い API を先に作ると手戻りになる。UI はブラウザで動く Web アプリとして作り、
Tauri は Python の起動とウィンドウだけを担当する殻として最後に足す。

## D17 スケッチフィレットは仮想交点を残す
角を丸めると元の角の点が形状から消えるが、そこに付いていた寸法の意味を保つため、参照されている
角の点は両線の延長上に拘束して残し、線の長さ寸法は仮想交点からの距離に付け替える。

## D18 式は「上から順」に評価する
寸法が参照できるのは変数と、自分より上のフィーチャーの寸法だけ。再生成が上から 1 回で済み、
循環が構造的に起きない（変数同士の循環だけ検出すればよい）。式は ast で解釈し eval は使わない。

## D19 履歴を返さないカーネルは、面メッシュから履歴・隣接を逆算する（2026-11-11）
usd-brep には面の生成元・変形元を返す API が無い（docs/PHASE0.md）。カーネルへの要求を
「形を作る」「面ごとの三角形メッシュを返す」に絞り、残りを `MeshTopoKernel` で求める。
- 押し出し・回転の面: 結果の面の点をスケッチ平面の座標に戻し、端面か、どのスケッチ要素の側面かを判定
- ブーリアン・フィレットの面: 点が入力のどの面の上にあるかで判定。どれにも乗らない面はフィレット面
- エッジ: 面メッシュの境界線分のうち別の面に接するもの（T 字の継ぎ目に備え、線分を細かく分けて判定）
- 平面: 頂点への平面当てはめ。円筒軸: 押し出し・回転の時点で分かるので記録し、ブーリアンで引き継ぐ
- 判定は「点と面の距離 < 許容値」。許容値はメッシュの弦誤差の 4 倍（モデル寸法の 0.4%）
欠点: 弦誤差より小さい形状の違いは区別できない。メッシュ化の分だけ遅い。
カーネルが本物の履歴を返せるなら、そちらを優先する（Kernel を直接実装すればよい）。

## D20 usd-brep を続ける。OCCT へ切り替える条件
形を作る機能は十分あり、履歴は D19 で補える。0b の後、適合テストの R1〜R3・R6 のどれかが
usd-brep の機能不足で通せないときに OCCT へ切り替える。上位層は Kernel IF しか使わないので影響しない。

## D21 カーネル形状は不変として扱う（usd-brep では演算前に複製）
フィーチャーツリーは前回の結果（形状）をキャッシュして再利用する（差分再生成）。usd-brep の
ブーリアンは入力を消費し、フィレット・移動・回転は入力を書き換えるので、アダプタは演算の前に
必ず `copy()` する。上位層から見た形状は常に不変。複製の分の時間とメモリは許容する。

## D22 面上スケッチの座標系は面の形に依存させない
原点 = 部品の原点を面へ投影した点、x = 世界の X を面へ投影した向き（X が法線に近ければ Y）。
以前は面の重心を原点にしていたため、寸法を変えて面が伸びるとスケッチが一緒にずれた（一般的な 3D CAD では起きない）。

## D23 3D 表示は自作の小さな WebGL2 ビューア
Three.js を使う予定だったが、開発環境（ネットワークなし）で読み込めず、画面を撮って確かめながら作れない。
必要な機能（面ごとの陰影、エッジ、ピック、回転/パン/ズーム）は 400 行程度で書け、外部依存が無いので
Tauri に包むのも簡単。スケッチ表示・寸法表示が重くなったら Three.js への移行を再検討する。

## D24 通信は当面 HTTP + JSON-RPC（標準ライブラリのみ）
WebSocket ライブラリが開発環境に無く、E1 の操作はすべて「要求 → 状態」で足りる。サーバから押し出す通知
（長い処理の進み具合など）が必要になったら WebSocket か Server-Sent Events を足す。
サーバは localhost のみで待ち受け、1 要求ずつ処理する（1 人用）。

## D25 開発用の簡易カーネル（prism）
押し出しと和だけを形状として計算するカーネル。usd-brep の無い環境でも UI を作り、確かめられるようにする。
差・回転・フィレットは KernelError（ツリーにエラーとして出る）。実利用は usd-brep。

## D26 再生成中の想定外の例外もフィーチャーのエラーにする
ブーリアンでのカーネルの失敗がツリー全体を止めていた（E1 で発見）。KernelError はそのフィーチャーの
エラーに、その他の例外も「内部エラー」としてそのフィーチャーに閉じ込め、ログに残す。

## D27 スケッチ編集中のロールバックは「表示用」で、文書には残さない
一般的な 3D CAD と同じく、スケッチを編集している間はモデルをスケッチの直後まで戻して見せる。これを文書の
ロールバックバーで行うと Undo のスナップショットや保存に紛れ込むので、`view_rollback`（保存・Undo の対象外）にした。

## D28 ドラッグは途中を記録せず、離したときに 1 操作として記録する
マウス移動ごとに Undo を積むと使い物にならない。最初の移動の前の状態を覚えておき、離したときに
`History.commit(label, before)` で 1 つにまとめる。

## D29 スケッチの原点は「固定点」として必要になったときに作る
原点へのスナップは、その位置に固定点を（無ければ）作って共有する。基準になる点が 1 つあるので、
寸法 2 つ程度で完全定義にできる（一般的な 3D CAD の原点への一致と同じ効果）。

## D30 アセンブリの保存は当面、パートの定義を中に含めた 1 ファイル（D34 で置き換え。旧形式として開ける）
パートを別ファイルで参照すると、パスの管理（相対パス・未保存のパート）が要る。USD 保存（S）で
reference に置き換えるまでは、使っているパートの定義を `.ucasm` に含め、開くとパートも開く。

## D31 部品のドラッグは「視線に垂直な平面」上で引っ張る
掴んだ点の 3D 位置（奥行き）が分からないので、部品の原点を通り視線に垂直な平面との交点の移動量を
部品の目標位置にする。ソルバが合致で許される方向に射影する（D11 と同じ重み付き最小ノルム）。

## D32 USD はテキスト（.usda）を自前で書き、定義は JSON 文字列で持つ（2026-11-11、S）
- pxr（OpenUSD の Python）は開発環境に入らず、利用者の venv にあるかも分からない。書く内容（Xform・Mesh・
  BasisCurves・reference・xformOp）は少なく、.usda は文字列で書ける。読むのは自分の定義だけなので、
  文字列リテラル 1 つを読む小さなパーサで足りる（他のツールで保存し直されても、引用符の種類が変わる程度なら読める）
- フィーチャー定義・合致を USD の prim/属性に分解すると、型の対応づけと読み込みの両方が要る。to_dict() の JSON を
  1 つの文字列属性に入れれば、保存形式のバージョンも JSON 側の `format` で管理できる
- 表示メッシュ・部品の Xform は他の USD ツールで見るための写しで、開くときは読まない（正は JSON）
- 本物の USD として開けるかは、利用者の PC で pxr があれば `scripts/s_probe_usd_export.py` で確かめる

## D33 BRep（omniSolid）はカーネルが書けたときだけ、別ファイルに書いて参照する
`Kernel.export(shape, path, "usd")` で `名前_body.usda` に書かせ、パートの `/Part/Body` から reference する。
書けなくても保存は失敗させず、警告として返す（開くときは定義から再生成するので BRep が無くても困らない）。prism は書かない。
- 利用者の PC で確認（usd-brep 1.0.1）: `usd.export_brep(brep, filename)`、BRep を読み戻した体積は元と一致（相対 5e-7）
- reference には参照先の prim パスが要るが、pxr が無いのでバイナリ（usdc）の中を読めない。拡張子を `.usda` にして
  テキストで書かせ、自前の簡易パーサ（`usdio.prim_specs`）で BrepArray の prim パスを探す
- 参照が正しく合成されることは、usd_brep の `import_breps` にパート・アセンブリのファイルを渡して確かめる
  （パート 1 個・同じパートを 2 回置いたアセンブリで 2 個読めること。`test_part_real_kernel.py`）
- 未確認: Omniverse など omniSolid を描くツールでは、BRep と表示メッシュ（/Part/Display）が重なって描かれるかもしれない

## D34 アセンブリはパートを reference し、保存時に必要なパートも保存する（D30 を置き換え）
一般的な 3D CAD と同じく、パートは別ファイルで、アセンブリはそれを参照する。パスは相対パス（フォルダごと動かせる）。
アセンブリを保存するとき、使っているパートが未保存・変更あり・旧形式なら一緒に保存する（一般的な 3D CAD は確認を出すが、
1 人用なので聞かずに保存し、何を書いたかを返す）。未保存のパートはアセンブリの隣に置き、既存のファイルは上書きしない。

## D35 寸法の向き（水平 / 垂直 / 平行）は置く位置で決め、既存の寸法の種類で表す（2026-11-11、スケッチの使い勝手）
一般的な 3D CAD のスマート寸法は、線や 2 点の寸法を置く位置で水平・垂直・平行が変わる。拘束の種類は既にある
（hdistance / vdistance / length / distance）ので、UI が置く位置から種類を決めて API に渡す。新しい種類は増やさない。
円は直径（一般的な 3D CAD の既定）にするため `diameter` を足した（半径変数 = 値 / 2）。
文字の位置は「既定の位置（測る 2 点の中点・円の中心・2 線の交点）からのずれ」で持つ。形が変わっても寸法が付いてくる。

## D36 エンティティ変換は「エッジ上」拘束 1 つで要素を固定し、再生成のたびに投影し直す
- 一般的な 3D CAD の「エッジ上」と同じく、モデルが変わると追従させたい。点の fix を並べると、投影し直すときに
  どの点がどのエッジ由来か分からなくなるので、要素ごとに 1 つの拘束（`on_edge`、投影元の永続名を持つ）にした
- 円弧は中心・始点を固定し、終点は向きだけ固定する（半径は始点が円上にある暗黙拘束で決まる。全部固定すると冗長）
- 隣り合う要素の端点は共有しない（共有すると同じ点を 2 つの拘束が固定して冗長になる）。輪郭は座標でつながる
- 形状はカーネルの表示用折れ線から当てはめる（カーネルに曲線の種類を問う API が無く、どちらのカーネルでも同じに動く）

## D37 寸法の値の編集はダブルクリック、シングルクリックは選択とドラッグ
文字をドラッグで動かせるようにするため（一般的な 3D CAD も、値の変更はダブルクリック）。寸法を新しく置いたときは、すぐ値の入力欄を開く。

## D38 作図中のスナップは API に「どこに合わせたか」を渡し、サーバが拘束を付ける（2026-11-12、U2）
一般的な 3D CAD は作図中に線上・中点などへ合わせると自動で拘束が付く。UI が座標だけ送ると拘束が付かず、後で動かすと離れる。
`sketch.add` の点に `{"mid": 線}` / `{"on": 線・円, x, y}` を許し、サーバが点を作って 中点 / 点-線上 / 点-円上 を付ける
（要素の追加と拘束が 1 回の Undo になる）。正接・平行などの推測はまだしない。

## D39 ミラーは点ごとの対称拘束で表す
専用の「ミラー」拘束は作らず、既存の対称（点, 点, 線）を点ごとに付ける。元を動かせば写しが追従し、拘束を消せば独立する
（一般的な 3D CAD も対称拘束が付く）。軸の上の点は写しを作らず共有するので、左右の輪郭が 1 つにつながる。

## D40 ファイルダイアログは Python 側で出す（別プロセスの tkinter）（2026-11-12、T）
Tauri の dialog プラグインを UI から呼ぶには、UI のページ（http://127.0.0.1）に IPC を許す設定（capability の remote）が要り、
ブラウザで開いたときは別の実装が要る。サーバが `python -c`（tkinter）を子プロセスで起動してパスを受け取れば、
ブラウザでも殻でも同じ RPC（`ui.pick_path`）で済み、サーバのスレッドで GUI を扱わなくてよい。
tkinter や画面が無ければ `available=false` を返し、UI は画面内の入力欄に切り替える（自動テストは環境変数 `AGENTCAD_NO_DIALOG`）。
ブラウザの `prompt()` は WebView で使えない場合があるので、画面内の入力欄（`askText`）に置き換えた。
追記（2026-11-14）: ダイアログの子プロセスには stdin を渡さない（DEVNULL）。デスクトップ版ではサーバの stdin が殻とのパイプで、
終了の合図を待つスレッドが読み続けているため、Windows ではそれを引き継いだ子の Python が起動の途中で待たされ、本体を閉じるまでダイアログが出なかった。

## D41 Tauri の殻は「Python を起動して窓を出す」だけにし、UI との間に入らない
- D16 のとおり Rust を最小にする。UI は殻の中でも `http://127.0.0.1:<port>/` を開くだけなので、ブラウザでの開発・自動テストがそのまま有効
- この開発環境では Tauri のクレートを取得できず、ビルドして確かめられない。確かめられない部分を減らすため、
  使う API を少なく（ウィンドウ作成・`eval`・状態・終了イベント）し、型は API の形を写した偽クレートで `cargo check` した
- サーバの準備ができるまで起動画面を出し、失敗の理由（Python が見つからない等）を画面に出す（コンソールが無いので）
- 殻が落ちたときにサーバが残らないよう、サーバは標準入力が閉じたら終了する
- 起動・ビルドは Tauri の標準どおり npm の tauri-cli（`npm run tauri dev` / `build`）。利用者が自分でコマンドを打つので、
  起動用のバッチファイルは作らない。インストーラも作らない（利用者の指示、2026-11-12）

## D42 フィーチャー作成は「すぐ作って、右のパネルで直し、✓ / ✗」にする（2026-11-12）
一般的な 3D CAD は PropertyManager で値を決めてから ✓ で作る（プレビュー付き）。こちらは作成ボタンでフィーチャーを実際に作り
（= プレビュー）、右のパネルに ✓ OK / ✗ キャンセルを出す。✗（Esc）は作ったフィーチャーの削除。プレビュー専用の仕組みを
持たずに同じ操作感になる。確定前でも Undo の履歴には入る（✗ の後に Ctrl+Z で復活できる）。

## D43 パターン・ミラーは、元のフィーチャーのツール形状を「置き直した平面」で作り直す
- カーネルに「立体を移動・回転・鏡映する」操作を足すと、履歴の逆算（MeshTopoKernel）にも手が入り、usd-brep での確認も要る。
  スケッチ平面（原点・x・法線）を変換して同じ押し出し・回転を実行すれば、確認済みの操作（押し出し・回転・ブーリアン）だけで済む
- カットのパターン（穴の並び）もそのまま動く。全貫通はインスタンスごとにその場所のボディの範囲で決まる
- 元にできるのは押し出し・回転だけ（フィレットなどは不可）。一般的な 3D CAD の「ジオメトリパターン」に近い

## D44 既にあるフィーチャーの参照を選び直すときは、表示をそのフィーチャーの直前まで巻き戻す
面・エッジの永続名は、後のフィーチャーが面を分けると変わる（`#2` が付くなど）。最終形状で選んだ名前は、
そのフィーチャーが作られる時点の形状には無いことがある。一般的な 3D CAD のフィーチャー編集と同じく、選ぶ間だけ
`view_rollback`（スケッチ編集で使っている表示用の巻き戻し）でそのフィーチャーの直前の形を見せる。

## D45 オフセットの正接部は「交点」ではなく「半径方向の線上」で決める
線と円弧が正接でつながる所は、オフセット後も正接になる。新しい端点を「線の上かつ円弧の上」と決めると重根になり、
ヤコビアンが落ちて冗長と誤判定される（D の正接と同じ問題）。新しい端点を「元の端点と中心を結ぶ線の上」に置く拘束
（`collinear`）に替え、その端点から決まってしまう拘束（線の距離、後から処理する円弧の半径差）は付けない。
スロット（正接だけの閉じた輪郭）のオフセットが冗長なしで元と同じ自由度になることをテストしている。

## D46 表示は平行投影・中ボタン回転を既定にする
一般的な 3D CAD の既定に合わせる（平行投影、中ドラッグ = 回転、Ctrl+中 = パン、Shift+中 = ズーム、Ctrl+1〜8）。
左ドラッグの回転と右ドラッグのパンは、中ボタンの無い環境（ノート PC）のために残す。右クリック（動かさない）はメニュー。
平行投影でも「距離」（`dist`）で拡大率を表し、見える範囲の半分 = dist × tan(視野角 / 2) とする
（スケッチのスナップ距離やドラッグの計算を透視投影と共通にできる）。

## D47 スケッチのツールはビューの上ではなくツールバーの下段に出す
ツールが 18 個に増え、ビューの上に浮かせると 2 行になって図を隠す。一般的な 3D CAD の CommandManager と同じく、
スケッチ編集中はツールバーの下段をスケッチのツールに切り替える（押し出し・カット・回転は残す）。
ツールバーの高さが変わらないので、スケッチの出入りでビューが上下に動かない。「スケッチ終了」はビューの右上（確認コーナー）。

## D48 面取り・シェルは k_probe のレポートの関数で作る（2026-11-12）
- 面取り: usd-brep に「エッジを選んで面取り」の専用関数は無い（`chamfer_fillet` は全エッジ）。`fillet_edges` の
  `xsect_type=0` が「円のフィレットが面に接する線どうしを平らにつなぐ」ので、90° のエッジでは半径 = 後退量になり、
  一般的な 3D CAD の「距離」の面取りと同じになる。エッジの特定はフィレットと同じ（エッジ上の点 → `find_edge`）
- シェル: `shell_brep`（取り除く面を `faces_to_shell`、負の距離で内側）。面の特定は、面の上の点（いちばん大きい三角形の重心）
  → `find_face`（`_face_meshes` で使って確かめた呼び方）
- 面の名前: 面取りの面は元のエッジ、シェルの壁は「厚さだけ離れた元の面」から付ける。どちらも元の名前が変わらない限り安定
- 簡易カーネルは対応しない（エラー表示）。形状は実カーネルのテスト（`test_chamfer_and_shell_on_real_kernel`）で確かめる

## D49 スケッチの原点は、まだ無ければ仮の参照 "ORIGIN" で選ばせる
原点の固定点は、作図で原点にスナップしたときにだけ作られる。それ以外では原点を寸法・拘束の相手にできず、
「矩形を原点から寸法で決める」ができなかった（利用者の指摘）。UI に仮の点 "ORIGIN" を置いて選べるようにし、
サーバが受け取ったときに原点の固定点を作る（作図のスナップと同じ `_origin_point`）。固定点を最初から作らないのは、
使わないスケッチに要素を増やさないため（保存・Undo の差分にも出る）。

## D50 部品・アセンブリごとのウィンドウ（2026-11-12）
一般的な 3D CAD のように文書ごとにウィンドウを持つ（利用者の要望）。Python サーバは 1 つのままで、どのウィンドウも同じサーバに話す。
- ウィンドウの中身は `/?doc=<文書ID>`。新しいウィンドウは、デスクトップ版では殻（Rust）が作る: サーバを `--shell-windows` で起動し、
  `ui.open_window` でサーバが標準出力に `@@agentcad:window <ID> <名前>` を出す → 殻が読んでウィンドウを作る（同じ文書のウィンドウがあれば前に出す）。
  Tauri の IPC を使わない方針（D41）を保つため。ブラウザでは `window.open`
- 同期: どの RPC にもウィンドウの ID（`_client`）を付け、サーバは文書を変える呼び出しごとに通し番号を進めて「だれが変えたか」を記録する。
  各ウィンドウは 1 秒ごとに `ws.rev` で「自分以外が変えたか」を聞き、変わっていれば状態を取り直す。パートを別のウィンドウで変えると、
  アセンブリのウィンドウの部品も追従する
- デスクトップ版では 新規パート・新規アセンブリ・開く が新しいウィンドウになる。ブラウザではポップアップを避けて今のウィンドウで切り替える
  （「⧉」で別のウィンドウに開ける）。アセンブリの部品の「開く」はパートのウィンドウを開く

## D51 合致は一般的な 3D CAD の手順（付けて見せて、ポップアップで選ぶ）
「合致」→ 面を 2 つクリック → 合う種類（平面どうし → 一致、円筒どうし → 同心、平面と円筒 → 正接）で合致をすぐ付けて部品を動かす →
ポップアップ（と PropertyManager）で種類・距離 / 角度・整列（同方向 / 反対方向）を変える → ✓ で確定して次の合致へ / ✗ で取り消し。
PropertyManager の ✓ で合致を終える。
- プレビューを別に計算せず、本当に付けた合致を変えていく（`asm.mate pending` → `asm.mate_set`）。作成と変更の Undo は 1 つにまとめる
- ✗（`asm.mate_cancel`）は作成の Undo で戻す（部品も元の位置に戻り、やり直しには残さない）
- 付けられる種類は幾何の組み合わせから決める（`Assembly.mate_options`）。距離・角度の初期値は今の配置の値（`Assembly.measure`）

## D52 ほかのスケッチの表示と、その点・線への外部参照
- 表示: 一般的な 3D CAD と同じく、どのフィーチャーにも使われていないスケッチは表示、使われたスケッチは隠す。右クリック（または右のパネル）で
  表示 / 非表示（`SketchFeature.visible`。None = 自動）。ツリーで選んだスケッチは必ず（青で）表示。3D でスケッチの線をクリックすると選べる
- スナップ: スケッチ中は、表示中のほかのスケッチ（ツリーで前にあるもの）を灰色の破線で描き、その点・線にスナップする。
  付く拘束は外部参照 `ext_point`（点に一致）/ `ext_line`（線の上）。`source = "スケッチID:要素ID"`、`data` は今のスケッチ平面に投影した座標で、
  再生成で参照先から計算し直す（エンティティ変換の `on_edge` と同じ仕組み）。参照先のスケッチは deps に入る
- スケッチから参照されただけのスケッチは「使われた」に数えない（隠れると参照できなくなるため）
- 線は直線だけ（円・円弧の上はまだ。点としては中心や端点を使える）

## D53 ツールバーは一般的な 3D CAD の配置（アイコン + CommandManager）
「ボタンを並べただけでは分かりにくい。寸法は重要」（利用者）。一般的な 3D CAD に合わせて 3 つに分ける。
- 標準ツールバー（1 段目、アイコンだけ）: 新規 ▾（パート / アセンブリ / デモ）・開く・保存・元に戻す・やり直し・文書・別ウィンドウ
- CommandManager（タブ: フィーチャー / スケッチ / アセンブリ）: よく使うものは大きいボタン（アイコンの下に名前）、仲間は小さいボタンを縦に積む。
  スケッチのタブは左端に「スケッチ」（スケッチ中は「スケッチ終了」）と、強調した「スマート寸法」。作図ツールは 3 段の格子、
  変換・オフセット・トリムは大きいボタン。スケッチを始めるとスケッチのタブ、終えるとフィーチャーのタブに自動で切り替わる
- ヘッドアップ ツールバー（3D ビューの上の中央）: 全体表示・正対・表示方向 ▾・表示スタイル ▾・透視
- アイコンは `app/web/toolbar.js` に SVG で持つ（外部ライブラリ・画像ファイルなし）。DOM は toolbar.js が組み立て、動作は app.js が ID で付ける
- 合致のポップアップの種類にもアイコンを付ける

## D54 スケッチの外へのスナップと、スマート寸法の相手（推測・自動スナップ）
「既にあるオブジェクトにスマート寸法を付けたい。円の中心・線の中点などのスナップを自動で」（利用者）。
- スナップ先: 自分のスケッチ（点・線の中点・線上・円上）に加え、ほかのスケッチ（点・線の中点・線上）とモデル（エッジの端点・中点、
  円 / 円弧エッジの中心、直線エッジの上）。印（端点 = □、中点 = △、中心 = ◎＋十字）はカーソルの近くだけ出す。確定すると外部参照の拘束
  （ext_point / ext_line）が付き、モデル・参照先が変わると追従する
- source の書き方を広げる: `"S:L@mid"`（ほかのスケッチの線の中点）、`"edge:名前@vertex|mid|center"`、`"edge:名前"`（直線エッジの上）。
  `@vertex` はどちらの端かを名前で決められないので、前の位置（作るときはクリック位置）に近い端。モデルを参照するスケッチはボディに依存する
- モデルのスナップ先は、UI が表示用メッシュのエッジ（折れ線）から計算する（サーバに一覧を問い合わせない）。サーバは同じ名前のエッジを
  カーネルから取り直して計算するので、表示の粗さは結果に影響しない
- スマート寸法の相手にスケッチの外を選ぶと、`sketch.reference` で参照の要素を作ってから寸法を付ける: 点 → 固定点、ほかのスケッチの線 →
  両端を固定した作図線、円・円弧 → 中心の点、モデルのエッジ → エンティティ変換と同じ投影の作図線・作図円。同じ参照は使い回す
- 推測線: 描くツールで、カーソルが既存の点（自分・ほかのスケッチ・モデル）と画面の縦・横に揃ったら座標を合わせ、青い点線を出す。
  拘束は付けない（一般的な 3D CAD と同じ）。正対していないときは使わない

## D55 選択の補助と計測（一般的な 3D CAD の選択フィルタ・ループ選択・別の選択・計測・質量特性）
- 選択フィルタ（ヘッドアップ ツールバーの左端）: すべて（面・エッジ）/ 面だけ / エッジだけ / 頂点だけ。フィーチャーの参照を選んでいる間
  （pickFor）とスケッチ中は効かない（そちらは選ぶ物が決まっているため）。頂点は計測でだけ使う
- 右クリック: エッジに「ループを選択」（カーソルの下の面の境界で、エッジ 1 本から同じループのエッジ）・「正接の連続を選択」（接線が 1° 以内で
  続くエッジ。フィレット用）、面に「別の選択…」（視線が通る面を手前から並べる。項目に乗ると光る。奥の面も選べる）
- 計測（評価のタブ）: 面・エッジ・頂点をクリックして足していく。1 つ → 座標 / 長さ・半径・中心 / 面積・法線・円筒の直径、
  2 つ → 形に合わせて 距離（中心間・垂直・平行な線 / 面の距離・軸間）・角度、3 つ以上 → 長さ・面積の合計。3D に寸法線を描く
- 質量特性: 体積・表面積・重心・外形寸法（密度は未設定なので質量は出さない）
- 計算は UI で表示用メッシュから（select.js）。平面・直線・円の組み合わせは正確。それ以外の最短距離はメッシュの点どうしなので「（近似）」と出す。
  サーバに正確な計測 API を足すのは、カーネルに距離計算が要るので後回し
- 当初の候補「スケッチの仕上げ（完全定義の要素を黒く）」は、要素ごとの定義状態の色分け（solve.entity_state）がすでにあったので見送り

## D56 アセンブリ: 干渉チェック・部品の複製とパターン・合致の編集
- 干渉チェック（`asm.interference`）: カーネルに形状の移動が無いので、表示用メッシュを部品の配置で動かして調べる
  （`cad/assembly/interference.py`）。外接箱が重なる組だけ、重なる箱の格子点（半格子ずらし）で「両方の内側」を数えて体積を近似。
  面が接しているだけは干渉にしない。格子より薄い食い込みは見落とすことがある。画面では一覧と、行を選ぶと場所を赤い枠で示す
- 部品の複製（`asm.copy`）: 同じパートをもう 1 つ、少しずらして置く（合致は付けない）
- 部品のパターン（`asm.pattern`、直線 / 円形）: 種の部品と同じパートを並べ、種に「ロック」の合致でつなぐ（種を動かすと形を保ってついてくる）。
  方向・軸は 選んだ面（平面 → 法線、円筒 → 軸）か座標軸。パターンとしての編集（個数を後から変える）はまだ無い（消して作り直す）
- 合致の編集: 合致の一覧で名前をクリック → 合致の PropertyManager とポップアップがその合致の面を選んだ状態で開く。変更は 1 回ずつ Undo に
  積み、✗ はその回数だけ元に戻す。作ったばかりの合致の変更をまとめる（D51）のは `asm.mate_set` の pending=True のときだけにした
  （以前は Undo の数だけで判断していて、Undo の後に編集すると作成と誤ってまとめることがあった）
- 部品の一覧の操作はアイコンにした（↗ 開く・⧉ 複製・📌 固定 / 🔓 解除・× 削除）。名前が切れないように

## D57 穴ウィザード
- 流れ（一般的な 3D CAD に近づける）: 面（か平面）を選ぶ → 「穴ウィザード」→ その面に位置のスケッチを作り点のツールに → 穴の中心に点を置く
  （スナップ・寸法も使える）→ スケッチ終了 → 穴ができ、右のパネルで種類・サイズ・終了条件・寸法を選んで ✓。一般的な 3D CAD は「タイプ」→「位置」
  の順だが、ここでは位置を先に決める（位置のスケッチを先に閉じておくと、種類を変えても位置が残る）
- 種類: ザグリ穴・皿穴・キリ穴・ねじ穴（下穴）・ドリル穴。サイズはメートル並目 M2〜M20（`cad/part/holes.py`。値は一般的な目安）。
  種類・サイズを変えると規格の寸法に置き換わり、寸法を直すとサイズは「カスタム」になる
- 形: 軸まわりの断面（ザグリ・皿・壁・ドリルの先端 118°）を 360° 回転してカット。カーネルに要るのは回転とブーリアンだけ。
  面と同じ所にカットの面ができないよう、断面は面より少し手前から始める。終了条件はブラインドと全貫通
- 穴の中心 = 位置のスケッチの、ほかの要素に使われていない点（固定点 = 原点の印は除く）。複数の穴の面の名前は `Hole1/side/wall`、
  2 つ目以降 `Hole1~2/side/wall`（辺: wall・tip・floor・cbore_wall・cbore_floor・csink）
- 直線 / 円形パターン・ミラーの元にできる（穴は位置ごとにツールを返す `tools()`）
- 簡易カーネル（prism）は回転もカットも無いので穴は作れない（エラー表示）。形は実カーネルのテストで確かめる
- ねじ山の表示（コスメティックねじ）はまだ無い

## D58 スイープ
w_probe（2026-11-12、usd-brep 1.0.1）の結果から決めた:
- カーネルは `sweep_along_planar_path(断面の曲線, 経路の曲線, move_profile=True)`。体積は理論値どおり（円 637.26 / 理論 637.22、
  管・閉じた経路も可）。経路は平面の上で、**始点から順に並べる必要がある**（逆順に並べると閉じた立体にならない）
- 断面は必ず経路の始点へ動かされる（move_profile=True は断面の外接箱の中心を、False は最初の曲線の始点を始点へ）。
  一般的な 3D CAD のように「断面をその場に置いたまま」はできないので、外接箱の中心を使い、断面が始点からずれていれば警告を出す。
  断面は経路の始点で経路に垂直に描く（垂直でなくても作れるが警告）
- 断面の向きは「経路の接線・経路の平面の法線」の組ごと回る（ねじれない）。長方形の断面をずらしたときの体積 380.53 が、
  断面の重心が描く線の長さ（パップス）と一致することで確かめた。面の名前付け（classify_sweep）はこの向きで、面の点を始点の断面へ戻して
  どの断面の要素から生まれたかを見る。面は 端の蓋 `<ID>/start`・`<ID>/end`、側面 `<ID>/side/<断面の要素>`（経路の区間ごとに分かれるので #n が付く）
- 経路 = 経路のスケッチの、作図線でない線・円弧（または円 1 つ）が 1 本につながったもの。始点は断面に近い端（閉じた経路は近い頂点）。
  逆向きにたどる円弧は arc_cw（時計回り）として渡す。usd-brep には曲線を逆向きにする関数が無い。最初は同じ円弧を反時計回りで
  渡していたが、経路が「前の曲線の終点から始まる」条件を満たさず S 字の経路が失敗した（2026-11-13、実カーネル）。今は反時計回りの円弧を
  作ってから、中心を通る弦の垂直二等分線のまわりに 180° 回して向きを逆にしている（`kernel/base.py` の arc_angles。点の集まりは同じで
  始点と終点が入れ替わり、平面の上に残る）
- フィーチャー `sweep`: profile（断面のスケッチ）・path（経路のスケッチ）・op（追加 / カット / 新しいボディ）。「スイープ」ボタンは
  選んだスケッチを断面にし、経路は「断面でない、いちばん新しい閉じていない線のスケッチ」を選ぶ。右のパネルで両方を選び直せる
- 簡易カーネル（prism）はスイープできない（エラー表示）。ねじり・ガイドカーブ・3D の経路はまだ無い
- ロフト・抜き勾配・リブは当面作らない（利用者）

## D61 作図中の推測（直角・正接・平行）とスケッチパターン
「スケッチ、断面の順で進めて」（利用者、2026-11-14）。一般的な 3D CAD の自動拘束と「直線 / 円形スケッチパターン」に合わせる。
- 推測: 線を引いているとき、始点につながった線に **直角**・円弧に **正接**、ほかの斜めの線に **平行** の向きが 3° 以内なら
  その向きに吸い付く（つながった相手を少し優先。水平・垂直の線は従来の H / V に任せる）。カーソルに ⊥ / T / ∥、相手の線を緑で示す。
  確定すると `sketch.add` の `relations` で送り、サーバは作った線が実際にそうなっているとき（角度の差 1e-4 以内）だけ拘束を付ける
  （線上・点へのスナップで向きが崩れたときに、矛盾する拘束を付けないため）
- パターン: 要素を選んで「直線スケッチパターン」（個数・間隔・向き）/「円形スケッチパターン」（個数・角度・中心。中心は既定で原点、
  「点を選ぶ」でスケッチの点）。右のパネルで値を変えるとビューに破線のプレビュー、✓ で作る（Undo 1 回分）、✗ / Esc で取り消し
- 写しには元と **等しい**（直線パターンの線は **平行** も）を付ける。**写しの位置は拘束しない**（寸法で決める）。一般的な 3D CAD のように
  間隔・角度を駆動寸法として残すのは、作図線と寸法が大量に増えて重くなるので当面やらない。選んだ要素どうしで共有している点は
  写しでも共有する（矩形などの輪郭は閉じたまま）。角度 360° は等間隔（360 / 個数）、それ以外は角度を 個数 − 1 等分

## D62 断面表示
「スケッチ、断面の順で進めて」（利用者、2026-11-14）。一般的な 3D CAD の「断面表示」（ヘッドアップ ツールバー）に合わせる。
- **表示だけ**（モデル・保存・計測は変えない）。サーバは関係なく、ビューア（`viewer.js`）の中で完結する。パート・アセンブリ・スケッチ中のどれでも効く
- 平面: 正面 / 平面 / 右側面、または選んだ平面（ツリー・参照平面）か面（面の法線は三角形の面積重み平均）。距離（スライダーと数値）で平行にずらす。
  平面の法線の側を消し、「反対側を表示」で逆。ボタンを押すと、平面・面を選んでいればそれで、なければ正面で切る（一般的な 3D CAD の既定）。
  ✓ で断面のままパネルを閉じ、ボタンをもう一度押すか ✗ でやめる
- 消す: 面・エッジ・ピックのシェーダで dot(法線, 位置) > 距離 を discard（消した側はクリックでも選べない）
- ハンドル（2026-11-14 追加。「普通の CAD のようにピボットカーソルで断面指定をしやすく」）: パネルを開いている間、平面の枠・
  青い矢印（法線の向き。ドラッグで距離）・赤と緑の輪（平面の中の 2 軸のまわり。ドラッグで平面を傾ける）をビューに出す。
  線は画面上で幅 3〜3.5 ピクセル（白い縁取り付き。WebGL の線は 1 ピクセルなので三角形で描く）、掴める所にカーソルを載せると黄色で太くなる。傾けると平面は「自由な平面」になり、距離はその平面から測る。✓ でハンドルを隠し、
  断面のボタンをもう一度押すとパネルとハンドルが戻る（開いているときに押すとやめる）。ハンドルの絵とドラッグの量は viewer、

- 切り口: ステンシルの偶奇。消していない三角形を奥行きなし・色なしで全部描いて INVERT し、奇数（視線上で立体の中）の所に平面上の板を
  奥行きありで描く。色は部品の色に面と同じ光を当てた色（切り口は +法線 を向いた平らな面として陰影を付ける）、さらに三角形と平面の交線を
  輪郭線として濃く描く（一般的な 3D CAD と同じ見え方。2026-11-14 に利用者の指摘でオレンジの一色から変更）。表示用メッシュが閉じていることが前提（カーネルの形は閉じている）。切り口のハッチングはまだ無い

## D64 再生成の速さ（実カーネル）
「車のモデルを読み込む時間が長い」（利用者、2026-11-14）。車のデモで 5.2 秒 → 2.4 秒（この PC、usd-brep）。

- Plane.to_world / y_dir を numpy なしにした（スケッチの点を 1 点ずつ変換するので、numpy の呼び出しの手間が効いていた）
- 残り（約 2.4 秒）の大半は、フィーチャーごとの面の対応づけ（meshtopo の match_sources: 履歴を返さないカーネルのために
  メッシュから逆算）とカーネルの tessellate。減らすには、カーネルの面の ID をそのまま使えるかの調査が要る

## D65 面の対応づけの高速化（実カーネル）
「フィーチャーごとに『どの面がどの面になったか』をメッシュから割り出す処理で高速化できるのであれば果敢に挑んで大幅に改善して」
（利用者、2026-11-14）。作業は git のブランチ perf-face-history で、計測 → 調査 → 1 論点ずつ実装・検証。
- 基準（この PC）: 車のデモの作成 2.32 秒、車の全体の再生成（width の変更）2.09 秒、板 0.073 秒（`scripts/bench_regen.py`）
- 調査（`scripts/p_probe_face_identity.py`）: usd-brep は演算の前後で面を追跡できない。面の hash は Python の一時オブジェクトの
  アドレスで、別の立体の面でも同じ値になる（A と B が同時に生きていても一致）。曲面（surface()）も copy・ブーリアンで別物になる。
  面に名前・属性を付ける関数も無い → カーネルの同一性は使えず、自前の対応づけ（meshtopo）を速くする
- 正しさの保証: 名前が 1 つでも変わるとフィレットなどの参照が壊れるので、新しい実装は古い実装と**同じ入力で同じ出力**を返すこととし、
  環境変数 AGENTCAD_CHECK_MATCH=1 のとき両方を計算して食い違えば例外にする（全テスト・車のデモで検査）。
  あわせて車と板の面・エッジの名前の一覧を前後で比べる（`bench_regen.py --names`）
- 実装（どれも「結果は元と同じ」を検査モード・名前の一覧で確かめた）:
  1. 三角形 → 面（usd_brep.py）: tessellate の face_varying_normals（角ごとの元の面の法線）で、面が変わる所を予測する
     （同じ面なら共有する頂点の法線が一致する・平らな面は同じ平面）。予測した区間の両端だけ find_face で確かめ、違えばその区間を
     二分探索、前提が崩れれば 1 枚ずつ。find_face は理想（区間あたり 2 回）に近い回数になった
  2. 面の対応づけ（meshtopo.match_sources）: 元の「入力の順に d < min(best, しきい値) なら更新」は「しきい値未満で d が最小、
     同じなら先の入力」と同じなので、（点, 三角形）の組を全部まとめて一度に計算する（組ごとの式は元の表の要素とビット単位で同じ）。
     外接箱で当選しようのない組を外し、平面の当てはめ（SVD）はしきい値の選び方で結果が変わりうる面だけにする
  3. weld は形ごとに KD 木を 1 回（近い頂点の組がある面だけ weld）、代表点・距離計算の下ごしらえも面をつないで一度に
- 結果（この PC）: 車の作成 2.32 → 1.57 秒、車の全体の再生成 2.09 → 1.28 秒（D64 の前の 5.2 秒からは 3 分の 1 以下）。
  面の対応づけは 437 → 74 ms。残りの 77% はカーネルの中（tessellate 0.44 秒・find_face 0.27 秒・ブーリアン等）
- やめたこと: カーネルの面の外接箱・平面で三角形の面を決める（候補が 1 面に絞れる三角形は 15% しかなく得にならない）、
  スレッドでカーネルを並列に呼ぶ（usd-brep は GIL を手放さない）、メッシュを粗くする（tessellate は粗くしても 1 回 40 ms ほどの
  下限があり、名前の入力が変わる危険に見合わない）
- 開発で meshtopo / usd_brep.py の面の扱いを変えるときは、`AGENTCAD_CHECK_MATCH=1` で全テストを流し、
  `bench_regen.py --names` の出力を変更前と比べる

## D68 形を変えなかったフィーチャーは警告。未定義のスケッチは (-) 表示

- 押し出し・回転・スイープ・穴の合成（`combine`）で、結果にそのフィーチャーの面が 1 つも無ければ警告
  「形が変わりませんでした（…）」。パターンの複製（ID に `~`）は既存の形とちょうど重なることがよくあるので対象にしない

## D69 外観（色）と、ファイルを開くときの進み具合
「開くのに時間がかかるので進捗を表示してほしい」「写真の装置を色付きで」（利用者、2026-11-14）。
- 外観: `PartDocument.appearance = {part, features, faces}`（"#rrggbb"）。優先は 面 > フィーチャー > パート（一般的な 3D CAD と同じ）。
  面の永続名の先頭がフィーチャー ID なので、フィーチャーの色は名前から引ける。パターン・ミラーの複製（`ID~n/…`）は、
  自身に色が無ければ元（seeds）の色を引き継ぐ。分かれた面（`…#2`）も同じ色。定義（JSON）に入るので保存・Undo の対象
- API `appearance.set {color, feature|features|face|faces}`。状態に `appearance`、メッシュに `part_color`・`face_colors`
  （形のキャッシュとは別に毎回計算する。色だけ変えても形は作り直さない）
- 画面: 頂点に色の属性（aCol）を足し、面のシェーダはその色で塗る。断面の切り口はパートの色。右クリック（フィーチャー・
  3D ビューの面・何も無い所）の「外観: …の色…」で色見本 16 色のパレット（「その他の色…」で OS の色選び、「色を解除」）。
  面とピックのプログラムが同じ VAO を使うので、属性の番号を bindAttribLocation で固定した
- 保存: `.usda` の表示メッシュに `primvars:displayColor`（三角形ごと）を書く（ほかの USD ツールでも色が付く）
- AI: render_view の画像も面の色で塗る。システムプロンプトに appearance.set（写真から作るときは実物に近い色を付ける）
- 進み具合: 開いている間、`Workspace.progress = {title, step, done, total}` を再生成がフィーチャーごとに更新
  （`PartDocument.progress` のコールバック）。最後に「表示の準備」（表示メッシュ）。画面は `ui.progress`（HTTP のロックの外）を
  0.2 秒ごとに見て、0.3 秒を超えたら棒とフィーチャー名・番号のダイアログを出す

## D70 「動かしてみる」モード（扉の開け閉め）と、大きな部品の合致の解けにくさの修正
「扉を開けたり閉めたりする挙動を」「インタラクティブモードとして別のモードにし、当たり判定を無視して滑らかに。やめたら元に戻ってよい。
計算量を減らし、コードも簡潔に」（利用者、2026-11-14）。
- 開閉そのものは既存の合致で表せる: ヒンジの筒どうしを同心円 + 端面を一致（回る自由度だけが残る）、開く角度は角度合致
- 「動かしてみる」（アセンブリのツールバー）: 入るときに `asm.joints`（部品ごとの回転軸 = 同心円の合致の相手の軸、世界座標）を
  1 回だけ取り、ドラッグ中は画面の中で部品の行列に軸まわりの回転を掛けて描き直すだけ（サーバも合致のソルバも呼ばない。
  ほかの合致・当たりは無視）。やめる（ボタン / Esc / 新しい状態が来る）と元の行列に戻す。文書も Undo も変わらない。
  最初に作った「合致の値のスライダー」（1 ステップごとにサーバで合致を解く）はこれで置き換えて消した
- 角度合致は cos で比べるので、0° と 180° では向き（どちらへ開くか）が決まらない。開閉には基準の面を斜め（例: 45°）にとる
  （装置の例ではヒンジの台座の角を 45° に落とし、閉 = 45°、90° 開 = 135°）
- ソルバ: 許容誤差の基準を変数（部品の位置）の大きさだけで決めていたため、部品が原点にあり形が m 単位だと厳しすぎて「矛盾」になった。
  `System.length_scale` に合致の幾何の大きさを入れる。さらに部品の原点から遠い軸のまわりの回転は、位置（mm）と四元数（1 程度）の
  大きさの食い違いで収束しなかったので、位置の変数を length_scale で割った単位で解く（`param_scale`、変数のスケーリング）。
  一度に 90° 回すと 300 回ほどかかるので、アセンブリの求解の上限を 100 → 500 回に
- 例: `Data/VacuumCoater_asm.usda`（本体 VacuumCoater_chamber と扉 VacuumCoater_door、Data は利用者のフォルダで git の外）

## D71 ファイルの読み込み・書き出し（STL・3MF・OBJ）。STEP は対応しない
「STEP や Blender、3D プリンタとやりとりできるファイルの読み込み・書き出し。難しそうな形式には対応しなくてよい」（利用者、2026-11-14）。
- 調査（`scripts/x_probe_io.py`、PHASE0.md 5 回目）: usd-brep に STEP などの入出力は無く、曲面の定義（NURBS の制御点・ノット）も
  取り出せない → STEP の正確な書き出しは作れない。三角形メッシュは取れる → メッシュの形式（STL・3MF・OBJ）だけにする
- 書き出し（`doc.export`、`cad/doc/exchange.py`・`meshio.py`。外部ライブラリなし）: パートはボディ、アセンブリは部品ごとに姿勢を
  反映したボディ。STL はバイナリで 1 つにまとめる。3MF（単位 mm）と OBJ（+ .mtl）は部品ごとの物体で、面の色（外観。D69）も書く。
  細かさ: 粗い / 標準（画面の表示と同じメッシュ）/ 細かい（弦誤差 = モデル寸法 × 4e-3 / — / 2e-4、曲面の角度 30° / — / 8°）。
  カーネルに `_face_meshes(raw, chord, angle)` の角度を足し、`MeshTopoKernel.export_mesh` で作り直す（面の番号は表示用と同じ）
- 読み込み: 「開く」で .stl / .3mf / .obj を選ぶと、インポートのフィーチャー（`import`）1 つだけの新しいパート（未保存）になる
  （一般的な 3D CAD で STL を開くのと同じ流れ）。ファイルの全部の物体を 1 つにまとめる。単位は mm（3MF は unit 属性を mm に直す）。
  色は読まない。メッシュは定義の中に zlib + base64 で持つ（元のファイルが無くても開ける）
- 取り込んだメッシュは「参照用のボディ」: 表示・計測・面上スケッチ・合致・図面・書き出しに使えるが、形を変える演算
  （押し出しの追加・カット・フィレット・シェルなど）はカーネルがエラーにする。BRep に組み直すのは難しい（三角形の数だけ面ができる）
- 面の作り方（`cad/kernel/meshbody.py`）: メッシュには面の区切りが無いので三角形の向きから作る。同一平面（0.5° 未満）でつながる
  三角形を平面の候補にし、なめらか（30° 未満）につながる隣の候補が無いか、その 4 倍以上大きいものを平面の面にする。残りは
  なめらかにつながる三角形どうしで 1 つの面（曲面）にまとめる。円筒・球のメッシュの帯・四角は同じくらいの大きさの隣になめらかに
  つながるので平面にならない。曲面には円筒を当てはめ、軸と半径を持たせる（同心・正接の合致に使える）。
  車のデモ（120 面）を書き出して読み直すと 113 面（違いは接する面どうしがまとまった分だけ）。球（64 万三角形）は 1 面、約 5 秒
- 面の名前は `Import1/F<番号>`（三角形の並び順で最初に現れた順。同じファイルなら同じ名前）
- STEP: 対応しない。必要になったら OpenCascade（`cadquery-ocp`）を足して「読み込みだけ・参照用のボディ」にするのが現実的

## D72 アセンブリの図面と、重複した面の名前の番号
「図面の階段の部分がおかしい」（利用者、2026-11-15）。マンションの作例（`Data/Mansion`）は階段を別パートにしてアセンブリで
6 層に並べていたが、図面はパートからしか作れず、住棟だけの図面に階段の柱と屋根だけが残っていた。
- 図面のモデルにアセンブリも選べるようにする（`Workspace.model_mesh` → `assembly_mesh`）。部品ごとのパートの表示メッシュを
  `Component.matrix()` で置いて 1 つにまとめる（面・エッジ・隣接の番号はずらす）。投影・隠線・寸法は今までのまま使える
- エッジ・面の名前は `<部品 ID>/<パートでの名前>`。同じパートを複数置いても寸法の相手を区別でき、パートを編集しても追従する
- 形が変わった印は「部品の ID・パートのボディ・姿勢」の組。変わったときだけまとめ直す。アセンブリは図面の側では解かない
  （部品の姿勢はアセンブリの API が状態を返すたびに解いた結果）
- 保存: モデルのアセンブリが未保存・変更ありなら一緒に保存する（パートと同じ。アセンブリの保存は使っているパートも保存する）
- 面の名前の番号（`_assign`）: 同じ名前が複数あると 2 つ目から `#2`, `#3`… を振るが、2 つのループの `start` と `start#2` の
  片方が分かれたときのように、元の名前に既に `#2` が付いていると同じ名前ができ、表を上書きして面が 1 つ消えていた
  （エッジの名前付けで KeyError になり、再生成が止まる）。使われている名前・ほかのグループの名前を飛ばして空いている番号を振る。
  衝突しないときの名前は今までと同じ
